# forms-tutorial notes

Files written (x5 locales pl, en, fr, de, pt_BR), all `php -l` clean, identical entry and option keys in all five (checked with a script):
- `api/lang/<locale>/help/tutorial.php`: 33 entries, 82 option lines each (phase 4, target 16, arranges 5, gift_rarity 5, trigger 26, completion 26).
- `api/lang/<locale>/help/guide.forms-tutorial.php`: 1 guide entry `tutorial` (label, help, 6 steps, example).

`tutorial.php` defines a local variable `$tutorialFacts` before `return` and uses it as the `options` of both `trigger` and `completion` (same 26 facts). `FieldHelp::read()` does `require $file` inside a method, so the variable lives in that scope; the name was chosen not to collide with `$files`, `$entries`, `$data`, `$file`, `$area`, `$locale`.

## Deliberate choices
- Option keys for the parametrised facts are written with the trailing colon (`cash:`, `car_level:`, `tires_mounted:`, `returned:`), the same strings that `TutorialFields` puts in the datalist (`SchemaChoices::conditionParameters()` + ':'). The integrator may want to match them without the colon; there is no `level:` fact (the player level is only used by `city_open`).
- NO `options` for `listing_vehicle`, `gift_part`, `reward_part`, `reward_garage`, although the input lists their values. Reason: their lists come from the pack/rules at runtime (`ContentOptions`, `cities()`), with names that the content already has in five languages, and `FieldHelp::html()` prints one `<li>` for every option that has a `help` (73 lines under each part select). If a test demands entries for them they can be generated from `content/packs/core/parts/*.json` and `vehicles/*.json`.
- The `label` of `goal`, `waiting`, `message`, `reply`, `decline` is probably not shown (`DefinitionFields::texts` uses `label: false` and the fieldset title comes from `admin.tutorial.*`); only the `help` (under the first language box) matters there.
- The texts contain `tires_mounted:rain` and `tires_mounted:offroad` (a colon followed by a letter, unavoidable because that is the real syntax). Harmless as long as nobody passes `$replace` keys `rain` or `offroad` to `FieldHelp`.
- The French files use U+00A0 before `:` `;` `?` `!` and `%` `$`, inside `« »`, and in thousands (`17 000`). EN/DE/PT use typographic quotes and apostrophes, no straight apostrophes.

## UNSURE
- `version`: nothing in the engine reads it (`TutorialSteps`, `Tutorial`); I wrote "the engine decides nothing from it". I did not check the pack manifest or exports for a link to this number.
- `listing_age_years`: only shown on the exchange (`UsedListing`); `buyListing` passes condition, price (as value) and mileage to the car, not the age. I wrote that it is shown with the offer.
- `first_run_fuel_ml` "about four laps": taken from `docs/api-runs.md` ("bak spada poniżej jednej czwartej po czterech okrążeniach"), not measured by me.
- `phase` boundaries: "first five minutes / first hour / first day / first week" are the schema's words; which real steps belong where I read from tutorial.json (1: wreck..refuel, 2: repair..travel, 3: offroad..away, 4: upgrade..network).
- "By custom no XP and no garage in phases 3-4": only a convention of the docs; the engine pays whatever the step has, and the economy check only counts phases <= 2, so an XP reward in phase 3-4 would not be seen by the `model.tutorial` comparison.
- `equipment_bought` also fires for bays and mechanics (`WorkshopGear::BAYS`, `MECHANICS` post the same ledger reason `workshop_gear`); my help says "workshop equipment (for example a tire machine)".

## Inconsistencies / things to know about the code
1. **A step with messages but without `reply` probably breaks `GET /tutorial`**: `TutorialResource` does `I18nText::from($step['reply'])` with no null check, the schema does not require `reply`, `TutorialForm`/`TutorialFields` mark it optional (`required: false`) and `PackValidator` does not check it (it only checks `decline` for optional steps). An undefined array key becomes an ErrorException in Laravel. My help says the step "should have it" and that the panel does not insist. Suggest: validate it (error in `checkTutorial`) or make the resource tolerant.
2. `acknowledged` as a trigger can never hold (a step with no row has no `acknowledged_at`), so it would stall the tutorial; documented in the fact's help. Not validated.
3. `recovered` is true for any run that is not broken, also before a breakdown ever happened; only meaningful after `breakdown`. Documented.
4. `job_queued`, `crate_opened`, `travel_started`, `travel_done`, `email_confirmed` count what the driver did EVER, while `merge_done`, `service_done`, `upgrade_done`, `car_bought`, `equipment_bought`, `garage_bought` count only since the step started. The schema description says so only for the second group implicitly; documented in the `completion` tip.
5. The server hard-codes three step keys that the schema does not mention: `repair` (breakdown stays scripted until it is done; `SimulateEconomy` leaves its cash out of the gifts), `mount` (first short mounting job, free first crate starts after it) and `crate` (free first crate until it is done). Renaming or deleting them silently changes the first hour. Documented in the `key` tip.
6. `PackValidator::checkTutorial` requires an exchange listing when `car_bought` is in the trigger OR the completion, but `TutorialScript::exchangeListing` offers the listing only while the active step has `car_bought` in its COMPLETION. A step with `car_bought` only in its trigger passes validation and never gets a listing.
7. A new step inserted into the live tutorial is started for every driver who has no row for it, including drivers further along or finished (`Tutorial::advance` visits every step without a row and starts it as soon as its trigger holds). Documented in the `steps` tip; worth knowing before adding steps in the middle.
8. `steps_hint` of the old `admin.tutorial` says "Kroku, w którym są gracze, nie można usunąć"; the real check (`DefinitionUsage::removedInUse`) only counts rows keyed by the step key, which is why renaming a key is refused too (documented in `key`).
9. `returned:n` stays true only until `TouchLastSeen` moves the mark again (at the earliest after 10 minutes of play), so a driver who comes back and does not open the game for a while may miss the step's trigger window; the step still starts the next time the mark is a long enough break, but the break is then no longer visible. This is how `Tutorial::returnedAfter` reads it; I only documented the "until the next visit mark" part.
10. The old `admin.tutorial.first_mount_ms` label ("Pierwszy montaż trwa najwyżej") is narrower than the real effect (it also caps every job in `arranges`); the new label is "Najdłuższe pierwsze zlecenie (ms)".
